# Protocol. Архитектура расширения

Версия 0.5, 2026-11-03. Ветка `online`. Дополняет `SPEC.md`, не заменяет.

## 1. Цель

Научить приложение принимать события извне: сообщения из групп WhatsApp и
Viber, письма, файлы. Приложение их не обрабатывает самостоятельно. Оно
уведомляет о событии по тому же протоколу, что и шаг, и только после
подтверждения человека выполняет действие по инструкции из конфига.

Делается не сразу. Сначала каркас, потом источники по одному.

## 2. Решения, принятые заранее

- **У WhatsApp и Viber нет логина с паролем и нет API для личного
  аккаунта.** Аккаунт привязан к номеру, переписка зашифрована сквозным
  шифрованием. Пути доступа и что мы с ними делаем:
  - служба чтения уведомлений (`NotificationListenerService`): официально,
    офлайн, аккаунту ничего не грозит; видит только новые сообщения, пока
    висит уведомление. **Основной путь**, см. 4.4;
  - экспорт чата из WhatsApp в текстовый файл: официально, даёт всю
    историю, но руками. Второй путь, через источник «файлы»;
  - эмуляция связанного устройства (whatsmeow, Baileys): полный доступ и
    ответы, но нарушение условий Meta и риск бана номера. Только на
    отдельном номере, если понадобится полный автомат. Не в плане;
  - Business API и резервная копия с root: не подходят.
- **Почта требует сети**, что противоречит SPEC 3 («полностью офлайн»).
  Сеть живёт только в отдельном модуле адаптера почты и включается отдельным
  вариантом сборки. Базовая сборка остаётся без разрешения INTERNET.
- **Полный DDD не делаем.** Проект маленький, автор один, общий язык уже
  есть в `SPEC.md`. Без агрегатов, репозиториев, шины событий, прикладного
  слоя и value object на каждый id. Лёгкая гексагональность: чистое ядро и
  интерфейсы на границе. Этого достаточно, пока не появится причина резать
  дальше.

## 3. Главный инвариант

**Действие наружу выполняется только внутри обработки ответа человека.
Никогда внутри такта.**

- Новый тип узла `action` достижим только через узел с ответом человека.
  Валидатор это проверяет так же, как сейчас проверяет ссылки и циклы.
- Исполнение узла `action` вызывается из `answerProc`. В `tick` нет кода,
  который может что-то отправить, переслать или переместить.
- На инвариант есть юнит-тест в ядре.

## 4. Устройство

### 4.1. Модули

- `:core`. Чистый JVM-модуль без Android. Сюда переезжают нынешние
  `config/` и `engine/` как есть, без переименований, вместе с тестами.
  Чистота проверяется компилятором: в модуле нет зависимости от Android.
- `:app`. Android. Экраны, приёмники, сервис, служба чтения уведомлений,
  файлы, будильники, хранение состояния. Сервис остаётся точкой сборки,
  где интерфейсы ядра связываются с реализациями.
- `:adapter-mail`, `:adapter-docs`. JVM-модули, появляются на своих этапах.
  IMAP и разбор документов тестируются без телефона.

### 4.2. Интерфейсы на границе ядра

Вместо одного `EngineListener` несколько узких интерфейсов. Ровно столько,
сколько нужно на текущем этапе, не впрок:

- журнал: строка лога и строка блокера, формат по SPEC 7.2 и 7.3;
- оповещение: момент сигнала и «состояние изменилось»;
- источник сигналов: адаптер отдаёт ядру сообщение для монитора;
- исполнитель действий: ядро отдаёт адаптеру действие из узла `action`.

Строковые события лога остаются как есть. Они контракт из спеки, по ним
правится конфиг. Переписывать их на классы событий не нужно.

### 4.3. Модель

Третья сущность верхнего уровня рядом с шагами и процессами: **монитор**.
Монитор читает сообщения из разрешённых ему групп, относит каждое к
категории и считает. К моменту шага протокола приложение уже знает, сколько
каких сообщений было. Монитор привязывается к шагу, и сводка дописывается
к вопросу шага.

В конфиге:

```json
"monitors": [
  {
    "id": "family",
    "source": "whatsapp",
    "chats": ["Семья", "Дача"],
    "categories": [
      { "id": "question", "label": "Вопрос", "contains": ["?"] },
      { "id": "other", "label": "Прочее" }
    ]
  }
],
"steps": [
  { "id": "evening_review", "time": "21:00", "check": "Разобрал чаты?",
    "monitors": ["family"] }
]
```

- `chats` это права доступа: сообщения из других бесед отбрасываются, не
  читаясь дальше названия беседы.
- `categories` это список «какие бывают». Засчитывается первая подошедшая;
  категория без условий ловит всё подряд. Пока условия только `contains`.
- Валидатор проверяет: `source` известен, `chats` не пуст, id категорий не
  повторяются, `monitors` у шага ведут на существующие мониторы.

В движке:

- Состояние монитора: засчитанные сообщения за текущий цикл, у каждого
  группа, категория, время, ключ дедупликации. Хранится в том же JSON, что
  остальное состояние. В начале цикла очищается, итог пишется в лог
  `MON_CYCLE`.
- Один новый метод: принять сигнал. Найти монитор по источнику и беседе,
  классифицировать, отсечь дубль, засчитать, записать `MON_MSG`. Чистая
  логика, тест без Android.
- Когда задаётся шаг с мониторами, к тексту на экране и в уведомлении
  дописывается сводка: «Семья: 12 сообщений, вопросов 3». Окно подсчёта: с
  начала цикла. Позже можно считать с прошлого закрытия того же шага.
- Текст сообщения в лог не пишется. В логе группа, категория, время.

Позже поверх засчитанных сообщений строятся **предложения действий**:
`Proposal` со статусами (ожидает, подтверждено, выполнено, отклонено,
просрочено), процесс с запуском по правилу, узел `action`. Это этап 5,
модель уточняется, когда монитор заработает.

### 4.4. Служба чтения уведомлений

- Разрешение «Доступ к уведомлениям» человек включает руками в настройках
  Android, программно нельзя. Приложение показывает, включено ли, и ведёт
  на экран настроек. Службу поднимает и держит система, отдельно от нашего
  сервиса.
- Из уведомления берётся структура MessagingStyle: название беседы и массив
  сообщений с отправителем, текстом и временем. Заголовок не разбираем.
- WhatsApp перевыставляет уведомление с полным массивом последних сообщений
  при каждом новом. Дедупликация по ключу «беседа, отправитель, время,
  текст» обязательна.
- Не приходят: сообщения, прочитанные в открытом чате на этом телефоне;
  сообщения из групп, замьюченных в WhatsApp; история до включения. Длинные
  тексты обрезаны. Для счётчиков хватает, для чтения переписки нет.
- В службе нет логики: фильтр по пакету, разбор, передача в сервис
  интентом, как сейчас делают кнопки уведомлений.

Что монитору **не мешает**:

- **Заблокированный телефон.** Служба работает в фоне независимо от экрана,
  уведомление создаётся системой при приходе сообщения. Исключение: после
  перезагрузки до первой разблокировки, пока хранилище зашифровано.
- **Чтение на ноутбуке.** Ноутбук это связанное устройство, телефон остаётся
  основным и получает всё сам. Уведомление создаётся в момент прихода,
  служба срабатывает сразу. Прочтение на ноутбуке снимает уведомление с
  телефона, но монитор его уже засчитал. Сокращается время, пока
  уведомление висит, а не факт его появления.

Что монитор **ломает**: группа замьючена в WhatsApp, уведомления WhatsApp
выключены в настройках телефона, прошивка убила службу. Всё проверяемо и
чинится настройками.

Проверка без кода, пять минут: заблокировать телефон, попросить написать в
группу, прочитать на ноутбуке, затем на телефоне открыть «Настройки,
Уведомления, История уведомлений». Если запись WhatsApp там есть, служба
её тоже увидела бы.

### 4.5. Экспорт чата как источник

Второй путь к WhatsApp, закрывает дыру монитора: когда нужна полная картина
за период, шаг протокола просит экспортировать группу, приложение разбирает
файл и пересчитывает по нему. Уведомления дают оперативный счёт, файл
точный. Ограничения:

- **Объём.** Без медиа последние 40 000 сообщений, с медиа последние 10 000.
  Для большой группы это хвост истории. Для счёта за день или неделю
  хватает.
- **Расширенная конфиденциальность чата.** Настройка 2025 года. Если её
  включил любой участник группы, экспорт отключён у всех. Для своих групп
  проверить один раз, для чужих может оказаться стеной.
- **Только руками и по одному чату.** Массового экспорта и автоматизации
  нет. Приложение становится получателем в системном меню «Поделиться»,
  тогда экспорт это четыре нажатия: группа, меню, «Экспорт чата», Protocol.
- **Что не попадает.** Сообщения «однократный просмотр», удалённые для всех,
  часть системных событий. Исчезающие попадают, пока не исчезли.
- **Формат нестабильный.** Простой текст, строка на сообщение: дата, время,
  отправитель, текст. Формат даты и разделители зависят от языка и региона
  телефона, многострочные сообщения идут продолжением без префикса, вместо
  медиа заглушки вроде «Медиа отсутствуют». Парсер пишется под этот телефон
  и проверяется на живом файле, не по описанию.
- **Регион.** На iPhone в Германии экспорт отключён. Android не касается.

### 4.6. Пересылка и рекомендация группы

Полная автономия на личном номере не решается: читать WhatsApp через
шторку можно, писать в произвольную группу без человека нельзя. В
постановке с подтверждением решается официальным путём: приложение
собирает готовое сообщение и открывает WhatsApp через системное
«Поделиться» с заполненным текстом, человек выбирает группу и жмёт
«Отправить». Автомат готовит, человек нажимает. Это и есть протокол:
уведомить, подтвердить, сделать по инструкции.

Рекомендация, куда переслать, строится **только по тексту и отправителю**.
Из уведомления приходит полный текст сообщения, отправитель и
группа-источник, этого достаточно. Список групп-получателей задаётся в
конфиге руками: WhatsApp список групп не отдаёт.

Чем рекомендация не занимается, сознательно:

- **Медиа.** Фото, документы, голосовые приходят заглушкой без текста.
  Не классифицируются, нас не интересуют.
- **Контекст.** Цитируемое сообщение в уведомление не попадает. Ответ без
  контекста никуда не маршрутизируется.
- **Очень длинные тексты.** Могут обрезаться системным лимитом на размер
  уведомления.

Такие сообщения попадают в категорию «посмотри сам». Цена ошибки
рекомендации: один лишний взгляд человека перед «Отправить».

Если группы можно перевести в Telegram, задача решается целиком и
официально: у него есть Bot API и клиентский API для личного аккаунта.
Для чужих групп в WhatsApp остаётся путь с подтверждением.

## 5. Этапы

Каждый этап сдаётся отдельно и даёт рабочий APK.

1. **Монитор.** Секция `monitors[]` и поле `monitors` у шага, валидация,
   состояние и лог, приём сигнала в движке с тестами, служба чтения
   уведомлений для WhatsApp и Viber, блок «Мониторы» на главном экране,
   сводка в тексте шага. Делается первым, до выделения ядра: главная
   неизвестность сейчас не архитектура, а что именно отдаёт WhatsApp в
   уведомлениях на этом телефоне. Код монитора живёт в `engine/` и чист,
   переезд в модуль потом механический.
2. **Выделение ядра.** Модуль `:core`, перенос модели, парсера, валидатора,
   редактора, движка и монитора, замена слушателя на интерфейсы из 4.2,
   тесты переезжают. Поведение не меняется.
3. **Файлы как источник.** Приём файла через «Поделиться» и выбор файла,
   разбор экспорта чата WhatsApp в сигналы для того же монитора. Даёт
   историю, которой нет у уведомлений.
4. **Хранилище сигналов.** База из SPEC 7.4, если состояние в JSON перестаёт
   справляться с объёмом засчитанных сообщений.
5. **Предложения действий.** `Proposal`, правила запуска процесса по
   сигналу, подстановка контекста, узел `action`, интерфейс исполнителя.
   Первый исполнитель ничего не делает сам, а показывает инструкцию
   человеку. Потом реальные: ответ в мессенджер через уведомление, ответ
   письмом, перенос файла.
6. **Почта.** `:adapter-mail`, IMAP, опрос из сервиса, учётные данные в
   зашифрованном хранилище, отдельный вариант сборки с сетью, правка SPEC 3.
7. **Документы.** `:adapter-docs`. Текст и CSV встроенно, PDF через лёгкую
   библиотеку, DOCX и XLSX по мере надобности.
8. **Классификатор.** Дополнение к категориям по `contains` за тем же
   интерфейсом, офлайн-модель на устройстве. Переписка наружу не уходит.

## 6. Чего не делаем

- Шина событий между контекстами.
- Прикладной слой с отдельным сценарием на каждую команду.
- Репозитории, агрегаты, value object ради чистоты.
- Модуль на каждый контекст. Один `:core` с пакетами.
- Переписывание строковых событий лога на классы.

Три правила, которые не дают превратиться в лапшу, и которые уже
соблюдаются для шагов и процессов:

1. Всё, что считает и решает, живёт в движке и покрыто тестом. Службы и
   приёмники только переводят чужой формат в наш.
2. Экраны читают движок и ничего не читают из служб напрямую.
3. Новая сущность входит одновременно в три места: конфиг с валидацией,
   состояние с сохранением, лог с событиями. Не в два из трёх.

Если через полгода контекстов станет пять и они начнут путаться, резать
дальше. Причина тогда будет видна.
