# Protocol. Архитектура расширения

Версия 0.1, 2026-11-03. Ветка `online`. Дополняет `SPEC.md`, не заменяет.

## 1. Цель

Научить приложение принимать события извне: сообщения из групп WhatsApp и
Viber, письма, файлы. Приложение их не обрабатывает самостоятельно. Оно
уведомляет о событии по тому же протоколу, что и шаг, и только после
подтверждения человека выполняет действие по инструкции из конфига.

Делается не сразу. Сначала каркас, потом источники по одному.

## 2. Решения, принятые заранее

- **У WhatsApp и Viber нет API для чтения групп с телефона.** Единственный
  путь без сервера: служба чтения уведомлений (`NotificationListenerService`).
  Она видит текст входящих, включая групповые, пока уведомление висит.
  Истории нет, длинные тексты режутся, сводки «N новых сообщений» приходят
  без содержимого. Ответ возможен через кнопку «Ответить» того же
  уведомления. Это ограничение источника, с ним не боремся.
- **Почта требует сети**, что противоречит SPEC 3 («полностью офлайн»).
  Сеть живёт только в отдельном модуле адаптера почты и включается отдельным
  вариантом сборки. Базовая сборка остаётся без разрешения INTERNET.
- **Полный DDD не делаем.** Проект маленький, автор один, общий язык уже
  есть в `SPEC.md`. Без агрегатов, репозиториев, шины событий, прикладного
  слоя и value object на каждый id. Лёгкая гексагональность: чистое ядро и
  интерфейсы на границе. Этого достаточно, пока не появится причина резать
  дальше.

## 3. Главный инвариант

**Действие наружу выполняется только внутри обработки ответа человека.
Никогда внутри такта.**

- Новый тип узла `action` достижим только через узел с ответом человека.
  Валидатор это проверяет так же, как сейчас проверяет ссылки и циклы.
- Исполнение узла `action` вызывается из `answerProc`. В `tick` нет кода,
  который может что-то отправить, переслать или переместить.
- На инвариант есть юнит-тест в ядре.

## 4. Устройство

### 4.1. Модули

- `:core`. Чистый JVM-модуль без Android. Сюда переезжают нынешние
  `config/` и `engine/` как есть, без переименований, вместе с тестами.
  Чистота проверяется компилятором: в модуле нет зависимости от Android.
- `:app`. Android. Экраны, приёмники, сервис, служба чтения уведомлений,
  файлы, будильники, хранение состояния. Сервис остаётся точкой сборки,
  где интерфейсы ядра связываются с реализациями.
- `:adapter-mail`, `:adapter-docs`. JVM-модули, появляются на своих этапах.
  IMAP и разбор документов тестируются без телефона.

### 4.2. Интерфейсы на границе ядра

Вместо одного `EngineListener` несколько узких интерфейсов. Ровно столько,
сколько нужно на текущем этапе, не впрок:

- журнал: строка лога и строка блокера, формат по SPEC 7.2 и 7.3;
- оповещение: момент сигнала и «состояние изменилось»;
- источник сигналов: адаптер отдаёт ядру `Signal`;
- исполнитель действий: ядро отдаёт адаптеру действие из узла `action`.

Строковые события лога остаются как есть. Они контракт из спеки, по ним
правится конфиг. Переписывать их на классы событий не нужно.

### 4.3. Модель

Рядом с `Step` и `Process` два обычных data class:

- `Signal`: источник, чат или отправитель, текст, вложения, время, ключ для
  дедупликации.
- `Proposal`: сигнал, правило, процесс, статус (ожидает, подтверждено,
  выполнено, отклонено, просрочено), срок жизни.

В конфиге новая секция `rules[]`: источник, чат, ключевые слова, какой
процесс запустить, срок жизни предложения. Проверяется тем же валидатором.
Процесс, запущенный правилом, получает контекст сигнала для подстановки в
тексты узлов.

## 5. Этапы

Каждый этап сдаётся отдельно и даёт рабочий APK.

1. **Выделение ядра.** Модуль `:core`, перенос модели, парсера, валидатора,
   редактора и движка, замена слушателя на интерфейсы из 4.2, тесты
   переезжают. Поведение не меняется. Самый ценный этап, остальное без него
   не строится.
2. **Сигналы и первый источник.** `Signal`, хранилище сигналов (база из
   SPEC 7.4), служба чтения уведомлений с фильтром по пакетам WhatsApp и
   Viber, дедупликация. В логе `SIGNAL_RECEIVED`. На главном экране список
   сигналов, без действий.
3. **Правила.** Секция `rules[]`, валидация, сопоставление сигнала с
   правилом, `Proposal` на главном экране.
4. **Подтверждение через протокол.** Процесс с запуском по правилу,
   подстановка контекста, узел `action`, интерфейс исполнителя. Первый
   исполнитель ничего не делает сам, а показывает инструкцию человеку.
   Потом реальные: ответ в мессенджер через уведомление, ответ письмом,
   перенос файла.
5. **Почта.** `:adapter-mail`, IMAP, опрос из сервиса, учётные данные в
   зашифрованном хранилище, отдельный вариант сборки с сетью, правка SPEC 3.
6. **Документы.** `:adapter-docs`. Текст и CSV встроенно, PDF через лёгкую
   библиотеку, DOCX и XLSX по мере надобности.
7. **Классификатор.** Дополнение к правилам за тем же интерфейсом,
   офлайн-модель на устройстве. Переписка наружу не уходит.

## 6. Чего не делаем

- Шина событий между контекстами.
- Прикладной слой с отдельным сценарием на каждую команду.
- Репозитории, агрегаты, value object ради чистоты.
- Модуль на каждый контекст. Один `:core` с пакетами.
- Переписывание строковых событий лога на классы.

Если через полгода контекстов станет пять и они начнут путаться, резать
дальше. Причина тогда будет видна.
